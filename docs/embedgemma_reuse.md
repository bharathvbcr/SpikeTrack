## 0. Bottom line

1. **The EmbeddingGemma 2 (EG2) vision tower is the closest thing in the stack to SAM's ViT trunk, and it already runs on the fast path: bf16 activations, fused QKV GEMM, tiled TensorOps attention at head dim 64.** EG2's whole 167M-parameter, 16-layer tower takes 57.5 ms (replica) / 58-63 ms (end to end) for one image of 2,520 padded patches in bf16, 2.9x faster than the same tower in exact f32 [V, `tessl/bench/results/embedgemma2_vision_speed_m5pro.txt`; `tessl/docs/embedgemma2.md:1358-1415`]. The recipe (not the tower) is what SAM should copy.
2. **Ojas's Metal `attention_forward` is a scalar kernel and is 26x-16x slower than tessl's `encoder_attn` at the SAM ViT shapes** (606 vs 22.8 ms global `[1,16,5184,64]`; 77 vs 4.75 ms windowed `[9,16,576,64]`, f32) [V, `ojas/bench/results/2026-10-26-attention-vision/README.md`]. The ojas-78 session has already routed the plain `Tq == Tk, D == 64` f32 case to `encoder_attn` on branch `gp/78-metal` (commit `fa5771c`), **not yet on Ojas main** [V, `git log main..gp/78-metal`]. What is not covered by that route, and what EG2 work could cover: bf16 operands (another ~2.5x at vision shapes), cross attention (`Tq != Tk`), additive bias (DETR boxRPB), and head dims 16/32. Details in sections 2 and 3.
3. **tessl's `encoder_attn` itself cannot do cross attention or a bias today, but the shared FlashAttention body (`attn_tiled.h`) already separates `Tq` from `Tkv` and holds the score tile in threadgroup memory, so both are small changes in the one kernel body rather than a new kernel** [V, section 2 rows 1-2].
4. **Not reusable as is:** EG2's 2-D RoPE kernel (rotate-half, mandatory QK/V RMSNorm, integer positions, per-image table), the tokenizer (refuses regex, ByteLevel and `end_of_word_suffix`, all of which SAM's CLIP BPE needs), the audio kernels, the vision pooler, and the Go embed server.
5. **Two items where SpikeTrack's notes have moved on or need a decision**, found while checking:
   - `COMPONENTS.md` / `HANDOFF.md` §10 (dated 2026-10-25, before the 10-26 Ojas merges) say Ojas has causal SDPA only and LoRA is Qwen3.5-only. Ojas main now has these as **trait methods** (`ojas/ojas-core/src/backend.rs`, `AttentionOpts { causal, window, bias, key_lens }` at `:373-378`): `attention_forward`, `conv2d_forward`, `conv_transpose2d_forward`, `max_pool2d_forward`, `interpolate_bilinear_forward`, `rope_interleaved_forward`, `layer_norm_forward`, `channel_layer_norm_forward`, `gelu_erf_forward`, `relu_forward`, `linear_bias_forward`, `softmax_forward` [V]. **A trait method is not a Metal implementation**, and the owner's "missing on Ojas Metal" list is still right for several of them:
     - Metal implementations on main [V]: `conv2d_forward` (im2col + tessl GEMM, only groups = 1, no dilation, and stride 1 or patch-embed stride = kernel; `ojas-metal/src/device.rs:2358`, `backend.rs:976`), `conv_transpose2d_forward` (kernel == stride, GEMM; commit `b3ce6f4`), `layer_norm` and exact GELU through tessl's `bert` kernels (`device.rs:3341-3367`), and `attention_forward` on the scalar `ojas_attn_gen_fwd` (`backend.rs:1786-1796`).
     - Metal-pending: `rope_interleaved_forward` Metal is on `gp/78-metal` only (commit `4897d82`), the `D = 64` attention route to tessl is on `gp/78-metal` only (`fa5771c`), and `relu` Metal has an untracked test (`ojas-78a/ojas-metal/tests/relu.rs`) with the main-branch commit `ceb1f84` being core + CPU only.
     - CPU-only or refusing on Metal as of `BUILD_REPORT-78.md:58,66,181` [V]: `interpolate_bilinear_forward`, depthwise conv2d, `max_pool2d_forward`, strided 3x3 conv; GroupNorm does not exist anywhere.
   - LoRA: `ojas-model/src/lora.rs` is model-agnostic (module doc: "Nothing here is specific to one model"); only its tests are Qwen3.5-specific [V]. See row 19 for the merge.
   - **The SAM 3.1 video path preprocesses with OpenCV, not PIL.** `Sam3MultiplexTracking.init_state` picks `video_loader_type = "cv2"` unless `use_torchcodec` (`external/sam3/sam3/model/sam3_multiplex_tracking.py:217-223`), and that loader does `cv2.cvtColor(BGR2RGB)` then `cv2.resize(..., INTER_CUBIC)` to 1008x1008 with no antialiasing (`external/sam3/sam3/model/io_utils.py:313-333`) [V]. The PIL/torchvision bilinear-antialias resize is the image-folder path (`io_utils.py:386-389`) [V]. If the video fixtures come from the cv2 path, a Pillow-exact bilinear resize will not match them [I]. This needs an owner decision on which loader defines "reference" for video; it is not an EG2 question but it decides whether tessl's `resize_rgb_u8` pattern (below) is useful.

## 3. Top five, ranked by value to the ≥3x-over-CoreML goal

1. **bf16 end-to-end ViT block on tessl's TensorOps path (rows 1, 4, 5).** The trunk is the largest known per-frame cost (about 5.4 TFLOP). Evidence: EG2's tower runs bf16 at 22-26 TFLOP/s GEMM and 12-13 TFLOP/s attention vs 5-6 in f32 (2.9x end to end). SAM trunk estimates [I], all from 4.6 TFLOP of linears and the Lane C attention medians: all-f32 about 1.0 s (4.6 / 5.7-6.5 TFLOP/s = 0.71-0.81 s GEMM, plus 224 ms attention via `encoder_attn` f32, plus elementwise); Ojas as it will be after `fa5771c` with Autocast bf16 GEMMs but f32 attention about 0.5 s (0.18-0.21 s GEMM + 0.22 s attention + bf16 copies and permutes); the full bf16 recipe about 0.3-0.35 s (0.18-0.21 s GEMM + about 0.09 s attention + elementwise). The CoreML backbone is about 2.05 s [V, `HANDOFF.md:16`].
2. **Generalise the tiled attention body for `Tq != Tk`, additive bias, key lengths, D=16/32 and bf16 D=32 (row 2).** This is the difference between the detector/tracker running at scalar speed (0.18 TFLOP/s, measured at D=64) and at matrix-unit speed. Memory attention (D=32 x 8 heads as built, `memory_attention.rs:20-22`; config.json reads 1 head of 256, see row 2; 5,184 queries x about 36k keys) is the most exposed and may exceed the trunk if it runs per object [I, [U] on multiplex sharing]. D=256 already exists in bf16; the missing piece for it is only `Tkv != Tq`. It is the only place where a missing EG2 feature (cross attention, bias) is not a nice-to-have.
3. **Fused QKV + RoPE + window-major layout kernel, modelled on `axial_qkv_norm_rope` (row 3).** Removes ~4 permute dispatches and finite checks per attention call (9 dispatches -> 1 kernel measured on the Lane C route) and fuses RoPE (EG2 measured RoPE at 4.4 % of the exact forward before sharing cos/sin across heads). Must be a SAM variant (interleaved, no norms), not EG2's op.
4. **GEMM epilogue fusion with `GeluErf` and a bf16-output LayerNorm (row 5).** Bias + residual + activation without extra passes over the `[5184, 4736]` MLP tensor; today tessl only has erf GELU as a separate f32 pass, which is the one EG2-era gap that blocks a clean bf16 SAM block.
5. **int8 GEMM `gemm_i8_dequant` (row 6): 45-57 TOP/s vs 22-26 bf16 measured.** Roughly 2x on the linear half of the trunk, but it needs per-token scale, an NT layout, an epilogue and a quality gate that does not exist; ranked last because the trunk is already well ahead of CoreML after items 1-4 [I].

Also worth doing, cheap, not ranked: `bench_paired` for the D6 claim (row 15) and `async_scope` in direct-tessl paths (row 14).
